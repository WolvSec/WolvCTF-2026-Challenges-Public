# Approved-ish — author notes (not for players)

**Category:** Web · **Target difficulty:** Medium · **Author:** Yichen Wu

The flag lives only in the required root `flag.txt`. `./build.sh` copies it into the `challenge/` and `healthcheck/` build contexts; those copies are generated and ignored by Git. Set the same value in CTFd. The player description is `description.md` and the handout is generated by `./build.sh` as `dis.tar.gz`.

## Intended solve

1. Create an alias to `sample-v1`, put it in a manifest, and approve the manifest.
2. The approval digest records alias IDs but not their targets. Direct PATCH and an exact-case backup restore refuse to change a locked alias.
3. Restore a backup with the alias ID in uppercase and target `restricted-v1`. The lock check uses the supplied ID's exact case, while the lookup and update use `COLLATE NOCASE`.
4. The old approval still matches the manifest. Snapshot export resolves the alias again under service authority and returns the restricted shard.

The UI supports the entire solve. It also hints that restore accepts legacy case variants. `solve/solve.py` is the reference solver and `healthcheck/healthcheck.py` checks the full chain against the real flag.

The deliberate vulnerability spans `workflow.py`, `storage.py`, `review.py`, and `exporter.py`. Do not normalize alias casing in the restore lock check or add a permission check in snapshot export until the challenge is retired.

## Build and host

```sh
./build.sh
kctf chal start
kctf chal status
```

`build.sh` produces the required `dis.tar.gz` and copies the current solver and flag into the healthcheck build context. The generated files are ignored by Git. Run it after any UI, solver, or flag change and before KCTF build/start. KCTF exposes HTTPS on internal port 8000 and runs a sidecar that periodically tests the full solve. The solver deletes its workspace on success and attempts deletion after a failed check; a failed delete makes a successful check unhealthy, while a failed check preserves its original error. If deletion itself fails, that workspace can persist until expiry or pod reset. The challenge image sets `COOKIE_SECURE=1` for HTTPS; the reference solver accepts that cookie on the sidecar's internal HTTP connection.

For local Docker Compose development only:

```sh
./build.sh
docker compose up --build -d
python3 healthcheck/healthcheck.py http://127.0.0.1:8000
```

Compose overrides `COOKIE_SECURE=0` for local HTTP. The image uses SQLite at `/data/approved.sqlite3`, stores only token hashes, and runs the app as uid 10001. KCTF mounts a writable 256 MiB `emptyDir` at `/data` with group 10001 because the challenge image's root filesystem is read-only; Gunicorn also keeps its worker heartbeat files there. The challenge container requests 100m CPU and 128 MiB RAM, with limits of 1 CPU and 512 MiB RAM. A container restart within the same pod keeps workspaces; pod replacement or rollout discards them. Expired workspaces are deleted when a new one is created. An older SQLite file gains the peer column on startup without deleting its sessions.

Session creation uses the actual TCP peer address (`request.remote_addr`), never a client-supplied forwarding header, to limit each peer to 64 live workspaces. A peer at its quota may replace its oldest empty workspace. At the global 2000-workspace cap, the oldest empty workspace is evicted. A workspace with aliases or manifests is never evicted by admission; if none are empty, new sessions receive 429 until one expires or is deleted. The full-solve sidecar also receives 429 and reports unhealthy at that point. A peer quota can affect unrelated players behind one shared ingress address, while distributed peers can still exhaust the finite global cap. Verify actual public ingress peer mapping and capacity behavior before release; use a trusted upstream rate limit or a different admission design if the ingress collapses all players onto one address. Use a maintenance window or shared storage if sessions must survive a rollout.

## Player handout and AI rule

`dis.tar.gz` contains only the UI's HTML, CSS, JavaScript, and a short player README. It contains no server code, solver, test files, or flag. The builder refuses to package the real flag. The live UI and browser network panel expose the normal workflow and API requests.

The player description and handout state a **challenge-specific no-AI rule** that covers direct and indirect use. This rule is not an event-wide claim and cannot technically prevent a player from using an AI service. The earlier full-source handout was solved by an AI agent in about 40 seconds; the black-box handout removes that direct code-reading shortcut. The new presentation still needs an independent human difficulty playtest.

## Verification

From this directory, after installing `challenge/requirements.txt`:

```sh
python3 -m unittest discover -s tests -v
./build.sh
python3 solve/solve.py http://127.0.0.1:8000
python3 healthcheck/healthcheck.py http://127.0.0.1:8000
```

The request tests cover workspace isolation, denied direct reads, atomic restores, the intended chain, invalid inputs, peer quota, and empty-only eviction at capacity. Local Docker and KCTF kind deployments passed their full-solve healthchecks. Before event deployment, build both KCTF images and confirm `kctf chal status` is healthy on the event's actual cluster.
